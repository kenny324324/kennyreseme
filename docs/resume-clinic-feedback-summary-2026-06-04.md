# 104 履歷健診回饋整理與求職策略修正

日期：2026-06-04  
用途：整理兩位前輩對履歷、作品集與職缺方向的建議，轉成 2026 年 6-8 月被動市場驗證與 9 月後正式求職的行動準則。

## 1. 這次回饋的總結

兩位前輩的建議其實很一致：你的作品集不是問題，職涯定位也不是問題；真正需要調整的是 **投遞時的職稱包裝、公司篩選條件，以及針對不同職缺的履歷關鍵字**。

目前最適合的對外定位仍然是：

> AI-native Mobile Product Engineer / iOS & Flutter App Developer

但如果是投特定 Flutter 職缺，履歷標題應該更直接：

> Flutter Engineer / Mobile App Engineer

中文可寫：

> Flutter 工程師｜具 App 上架、Firebase、產品協作與 UI/UX 整合經驗

原因是：公司或 HR 搜尋履歷時，會先看職稱與關鍵字是否對職缺。`AI-native Mobile Product Engineer` 適合放在個人定位或 Summary，但如果投 Flutter 職缺，標題要先讓對方明確知道你就是 Flutter 候選人。

## 2. 第一位前輩的建議分析

### 他看到的優勢

- 作品集網站完整，專案說明、技術流程與介面介紹都清楚。
- PM 經驗不會模糊職涯定位，反而能證明你有需求對接、流程理解與跨部門協作能力。
- 你的 UI/UX、App 開發、產品實作能力已經有被作品集充分呈現。

### 他提醒的風險

第一位前輩最重要的提醒是：你現在的公司看起來比較像接案型公司，所以你接觸很多不同 App，但可能比較少碰到：

- 長期產品維護
- 版本迭代
- 使用者回饋後的調整
- 數據觀察與產品優化
- 一個產品持續 6-12 個月以上的 ownership

這點會影響你下一份工作的選擇。你不只是要找 App Engineer，而是要找能補足「長期產品經驗」的 App Engineer 職位。

### 應該採納的結論

下一份工作應優先找：

- 公司有自有產品，而不是純接案。
- App 是核心產品或核心使用者入口。
- 團隊會長期維護與迭代，而不是只做階段性功能。
- 工程師能接觸使用者回饋、數據、版本優化與產品 roadmap。
- PM / Designer / Backend / QA / Mobile Engineer 分工清楚，但你也能參與產品討論。

要小心的職缺：

- 職稱寫 App Engineer，但實際只是短期交付。
- App 只是行銷活動頁、WebView 包裝或內部工具，不是核心產品。
- UI/UX、PM、工程全部混在一起，但沒有明確成長路線。
- 做完功能就換下一個案子，沒有長期維護與迭代。

## 3. 第二位前輩的建議分析

第二位前輩針對的是更具體的投遞策略，尤其是 Flutter 與全遠端職缺。

### 他的核心建議

1. **針對目標職缺改職稱**
   - 如果投 Flutter 職缺，履歷職稱可以直接改成 Flutter 工程師。
   - 這不是否定 Mobile Product Engineer 定位，而是讓 HR / ATS / 主管一眼看懂你符合職缺。

2. **全遠端職缺重視非同步協作**
   - Full Remote 團隊通常更重視獨立開發、解決問題、文件化與清楚溝通。
   - 你不能只寫「熟悉 Flutter」，要寫你如何遠端協作、如何把需求拆成文件、如何讓 PM/Designer/Backend 少來回。

3. **Flutter 關鍵字要更精準**
   - 不要只寫 Flutter。
   - 要補狀態管理、API、地圖、本地儲存、Firebase、上架、測試、版本管理等具體關鍵字。

4. **UI/UX 能力要保留**
   - 對遠端新創來說，懂 UI/UX 的工程師可以降低溝通成本。
   - 你的 UI/UX 不是要轉成純設計師，而是要包裝成「能把設計、產品與工程快速接起來」。

### 應該採納的結論

投 Flutter / 遠端職缺時，你的履歷要更像這樣：

> Flutter Engineer with product sense, App Store release experience, Firebase integration, and UI/UX collaboration ability.

中文可以寫：

> 具產品感的 Flutter 工程師，熟悉 Firebase、App 上架、跨部門協作與 UI/UX 介面落地。

## 4. tripool 職缺判斷

前輩分享的職缺是：

- 公司：Tripool 旅步 / 玩島玩旅行社
- 職稱：Flutter 工程師 | 旅遊新創
- 地點：104 顯示高雄，但工作方式為全遠端
- 薪資：104 搜尋結果顯示月薪 55,000-70,000 元
- 年資：2 年以上
- 技術：Flutter、Firebase、iOS、Android、GitHub、Git、SEO
- 工作內容：React 行銷頁、Flutter 行銷相關頁面、RESTful API、WebView、App 打包上架、效能與 SEO 優化
- 福利：完全遠端、自由安排上下班、每季 team building、基本法定項目

### 適合你的地方

- 全遠端，適合驗證你是否能走 remote Flutter。
- 旅遊與交通場景能接上你做過的跳蛙公車、FindToilets、Pickup。
- 需要 Flutter、Firebase、上架與 UI/UX 協作，和你的 Mish / SoulFeed / 個人 App 經驗有交集。
- 新創步調快，會需要能自己拆需求、快速做 prototype、減少溝通成本的人，這和你的 AI-assisted workflow 可以連上。

### 需要注意的地方

- 薪資 55,000-70,000 元偏低，低於你 9 月後應該挑戰的主目標區間。
- 工作內容看起來有不少 React 行銷頁、WebView、SEO 與行銷活動頁，不一定是核心 App 長期產品開發。
- 「全遠端」是亮點，但 GoodJob 上有一則 2026 年 3 月面試經驗提到福利普通、最大福利是遠端，薪資如 104 範圍。這是單一匿名經驗，不能當定論，但值得面試時確認。
- 如果職務主要是行銷頁和 WebView，對你的長期產品能力補強有限。

### 初步結論

tripool 可以當作「遠端 Flutter 市場驗證職缺」，但不一定是 9 月後最理想的主目標。

它適合拿來問問題、練職缺判斷、確認遠端 Flutter 團隊看重什麼；但如果薪資仍是 55,000-70,000，且工作內容偏行銷頁 / WebView，除非你非常重視全遠端，不然不應該排在優先 offer。

## 5. 兩位前輩建議合併後的新判斷標準

未來看職缺時，不只看職稱是不是 Flutter / iOS，而要用下面這張表判斷。

| 判斷項目 | 好訊號 | 風險訊號 |
|---|---|---|
| 公司型態 | 自有產品、長期營運、App 是核心入口 | 接案、短期專案、行銷活動頁 |
| 工作內容 | App 功能、架構、API、上架、迭代、使用者回饋 | WebView、短期頁面、單次活動、純切版 |
| 團隊協作 | PM / Designer / Backend / QA 分工清楚 | 工程師什麼都包，但沒有產品 ownership |
| 遠端成熟度 | 文件清楚、非同步協作、明確任務管理 | 只說可遠端，但流程不清楚 |
| 薪資 | 年薪可往 90-130 萬以上談 | 月薪 55,000-70,000 且成長性不清楚 |
| 技術成長 | Flutter 架構、狀態管理、測試、CI/CD、release | 只做 UI、WebView、簡單 API |
| 產品成長 | 能參與 roadmap、數據、回饋、版本優化 | 做完需求就結束 |

## 6. 履歷修改建議

### 通用版本

用於作品集首頁、LinkedIn、自我介紹：

> AI-native Mobile Product Engineer / iOS & Flutter App Developer

中文：

> AI 原生行動產品工程師｜iOS / Flutter｜具產品設計感與 App 上架經驗

### 兩個履歷版本

第二位前輩補充後，履歷版本可以更明確分成兩套。

#### A. Flutter 職缺版本

用於 tripool、FUNDAY、Jubo 或其他明確寫「Flutter 工程師」的職缺。

> Flutter Engineer / Mobile App Engineer

中文：

> Flutter 工程師｜熟悉 Firebase、App 上架、產品協作與 UI/UX 整合

也可以用：

> Mobile Engineer (Flutter)

這是針對該職缺的關鍵字優化，不代表要把自己包裝成純 Flutter senior。HR 和主管第一眼會先確認你能不能接 Flutter 專案，所以 Flutter / Dart / 狀態管理 / Firebase / 上架經驗要放最前面。

履歷 Summary 可寫：

> 具 Flutter、Firebase、RevenueCat 與 App Store 上架經驗，曾獨立完成閱讀紀錄 App Mish 與 AI 互動 App SoulFeed。熟悉使用 AI agent 加速 prototype 與功能開發，並能透過實機測試、文件化與跨部門溝通確保 App 交付品質。

#### B. App / Mobile Engineer 版本

用於比較廣義的 App Engineer、Mobile Engineer、Mobile Product Engineer 職缺。

> Mobile App Engineer (Flutter & iOS/SwiftUI)

中文：

> Mobile App 工程師｜Flutter & iOS/SwiftUI｜具產品協作與 App 上架經驗

這個版本保留你的多平台能力，尤其適合沒有限定 Flutter 或 iOS 的 Mobile Engineer 職缺。

### SwiftUI 背景不是弱點

第二位前輩補充的重點是：面試官其實會欣賞「有 iOS 原生開發背景的 Flutter 工程師」，因為這代表你有機會處理純 Flutter 工程師比較不熟的部分：

- iOS 原生設定與 App Store 上架
- Plugin / native bridge 整合
- 推播、權限、背景限制、深層連結
- iOS 使用者體驗與 Apple guideline
- Flutter 在 iOS 上的 platform-specific 問題

因此你的 SwiftUI / iOS 經驗不是 Flutter 投遞的弱點，而是可以被包裝成護城河。重點是：投 Flutter 職缺時，Flutter 仍要放第一順位，iOS/SwiftUI 放成跨平台背景與底層整合能力。

### Flutter 技術關鍵字要補

目前履歷可以再補這些字，讓 HR 和主管更容易看懂：

- 狀態管理：Provider；如果你接下來補 Riverpod 或 Bloc，就加 Riverpod / Bloc。
- API 串接：RESTful API、Dio / http、JSON parsing、error handling。
- Firebase：Firestore、Authentication、Cloud Functions、FCM、Crashlytics。
- 本地儲存：SharedPreferences、Hive / SQLite；依你實際用過的填。
- 上架：App Store review、TestFlight、RevenueCat、subscription、privacy policy、EULA。
- 遠端協作：Notion docs、async communication、spec writing、bug tracking。
- UI/UX 落地：Figma to Flutter UI、responsive layout、design handoff、prototype iteration。

注意：只寫你真的做過或近期能補起來的內容。不要為了關鍵字亂塞，面試會被追問。

## 7. 面試或初談要問的問題

### 判斷是不是自有產品與長期迭代

- 這個職缺主要是負責公司自有產品，還是客戶專案？
- 目前 App 是長期維運中的產品，還是階段性的新功能 / 新專案？
- 工程師在功能上線後，是否會參與後續版本優化、使用者回饋或數據觀察？
- 這個職位未來 6-12 個月主要會負責哪些產品目標？

### 判斷 Flutter 工作內容是否夠核心

- Flutter 主要負責核心 App 功能，還是行銷頁、WebView 或活動頁？
- 目前 Flutter 專案使用什麼狀態管理？Provider、Riverpod、Bloc 還是其他？
- App 是否有既有架構、測試、CI/CD、release 流程？
- 團隊如何處理 crash、效能、版本更新與 App Store / Google Play 審核？

### 判斷遠端團隊是否成熟

- 團隊是全遠端還是部分遠端？
- 遠端協作主要使用哪些工具？例如 Slack、Notion、Linear、Jira、GitHub。
- 任務規格、設計稿、API 文件通常會整理到什麼程度？
- 每週會議頻率如何？是否支援非同步溝通？

### 判斷薪資與成長性

- 這個職位的薪資範圍大約落在哪裡？
- 是否有年終、分紅、調薪、股票或其他績效制度？
- 如果職位是資深 Flutter 工程師，公司對 senior 的期待是技術主導、架構設計，還是單純開發速度？

## 9. 目前結論

兩位前輩的建議讓原本策略更清楚：

1. **作品集不用大改，方向是對的。**
   - 作品集已經能證明 UI/UX、App 開發與產品實作能力。

2. **PM 經驗要保留，但要包裝成產品協作能力。**
   - 它不是模糊定位，而是 Mobile Product Engineer 的加分項。

3. **下一份工作要補「長期產品迭代」經驗。**
   - 避免再進入純接案或短期交付環境。

4. **投 Flutter 職缺時，職稱要直接改成 Flutter 工程師。**
   - `AI-native Mobile Product Engineer` 是總定位；`Flutter Engineer` 或 `Mobile Engineer (Flutter)` 是職缺投遞版本。

5. **投 App / Mobile Engineer 職缺時，用更平衡的標題。**
   - 建議用 `Mobile App Engineer (Flutter & iOS/SwiftUI)`。

6. **SwiftUI / iOS 是 Flutter 投遞的護城河，不是弱點。**
   - 投 Flutter 職缺時，Flutter 放第一順位；iOS 放成 native integration、App Store、platform-specific 問題解決能力。

7. **全遠端職缺要強調非同步協作與文件能力。**
   - 這是你 Notion、PM 協作、AI-assisted workflow 可以發揮的地方。

8. **tripool 是可討論職缺，但不是最優先 offer。**
   - 全遠端是亮點，薪資與工作內容要確認；如果偏行銷頁 / WebView，就不符合你要補長期產品經驗的目標。

9. **2026 年 6-8 月繼續被動驗證，9 月後正式投遞。**
   - 目前收到 FUNDAY 這類 Flutter 邀約是好訊號，但現階段主要目標是蒐集市場資訊，不是立刻換工作。
